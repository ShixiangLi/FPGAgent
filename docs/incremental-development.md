# 顺序增量开发初版

本版将“规划后一次输出完整工程”改为“规划任务清单，再逐项交付文件”，不引入并行、多智能体或通用插件调度。

## 运行

命令与之前一致，例如：

```powershell
.\.venv\Scripts\python.exe main.py run --effort high --request "开发一个8位无符号加法器，输入a、b、cin，输出sum和cout。只仿真，不上板。自检覆盖进位和边界，并用Python生成真实波形图片。"
```

模型先明确需求和接口，规划 `development_tasks`。每项包含id、目标、依赖、输入文件、输出文件和交付条件。任务按依赖顺序执行，每项交付1至3个文件；后续任务按需读取已有文件。所有文件完成后仍使用原有集成仿真、Python绘图、构建、独立审查和按需上板流程。

## 任务内的小步执行

同一个任务也可以分多轮完成。模型每轮执行一个动作：读取文件、保存检查点、最终交付或提问。简单任务仍可直接交付完整文件；复杂任务先整理一个具体下一步，再逐段实现，不要求一轮完成全部推演和代码。

检查点动作示例：

```json
{
  "action": "checkpoint",
  "summary": "累计交接：接口已确定，PWM检查已写入，边界和复位检查待完成；尚未运行仿真",
  "next_step": "只补充复位后第一次计数的断言",
  "edits": [{"path": "sim/tb_top.sv", "old": "// RESET_CHECK", "new": "复位检查代码"}],
  "compact": false
}
```

`summary` 是模型持续维护的累计交接摘要，包含已确定决策、已完成内容、未解决问题、验证状态和来源路径，不是私有思考原文。`edits` 可省略，让模型先整理任务；`old` 为空只用于创建新文件，更新时必须唯一匹配已有文本。一个动作中的修改全部匹配并通过文件接口检查后才暂存，匹配失败直接反馈实际错误，不部分应用。

工作草稿保存在 `editing/<摘要>.json`，可以暂未完成，但不会送入仿真或记为交付。模型完成当前任务后返回 `deliver`，框架才将完整产物合入 `draft.json`。文件内容、当前任务、确认需求或方案变化会形成不同的编辑会话，避免复用不匹配的旧工作。

`working.md` 展示当前摘要、下一步、暂存文件、恢复状态和反馈。每个成功小步都会保存，因此中断恢复可以继续修改现有草稿，而不必重新生成整个文件。模型请求中的 `task` 使用最新 `next_step` 作为本轮目标，`full_task` 保留完整任务及交付条件；无需重新输出整个任务的实现。

## 按需compact与截断处理

开发上下文保留完整的已确认需求、设计、测试方案和工程接口，省去全局任务清单和旧进度日志。源码按窗口读取，每次最多请求8000字符；相邻或重叠片段合并到同一窗口，累计最多48000字符，避免反复切换前后两段。超过累计上限或读取不相邻片段时切换窗口。返回 `file_views.next_offset`，后续可换offset继续读取。完整文件始终保留在交付文件或工作草稿中。

读取窗口总量超过60000字符，或近期动作达到6条时，框架整理窗口至不超过48000字符、保留最近两条动作。模型也可在更新累计摘要后设置 `compact=true` 主动释放读取窗口。compact保留模型已写出的摘要、下一步、全部文件和已确认输入，不额外调用一个摘要智能体，不把文件删除或压缩成摘要。

API返回 `finish_reason=length` 时，客户端只保存原始响应与实际用量，抛出明确的截断结果，不自动降强度、加预算或直接重试。开发循环捕获后保存现有工作、释放读取窗口，并将截断事实存入独立的 `recovery` 状态；此时本轮目标只要求整理短检查点、选择更小的下一步。

恢复期间允许读取文件或提问，但这两个动作不会清除 `recovery`；临时接口错误仍使用 `feedback` 独立反馈。只有合法且不含代码修改的 `checkpoint` 才能退出恢复状态。提前交付或在恢复检查点中写代码会返回明确的协议错误，不应用修改。下一轮的 `task` 才切换到新选定的小步骤。中断、暂停、compact均保留恢复状态；旧版保存在feedback中的截断记录在续接时自动迁移。残缺JSON和未返回的思考不会被当成进展或可执行代码。

每批最多16轮；连续3轮没有新的读取窗口、摘要或文件修改，或本批两次生成截断时，保存为 `development_paused`，退出码为2。`--continue` 直接继续相同计划和工作检查点，不以“暂停”为由重新规划。缺少真实需求条件时仍使用 `clarify` 等待用户回答。

这里的compact是基于持久化摘要和文件的上下文重建，不是恢复被截断的模型内部推理，也不保证每个复杂任务都能完成。需求分析、方案生成和独立审查仍沿用各自的既有流程；这版不另加全阶段调度器。

在开发前先执行两次交互确认：

1. 模型只分析需求，展示验收条件、仿真/构建/上板与绘图范围；用户明确确认后才生成方案。
2. 展示设计与测试方案，包含激励、预期结果、自检方法、边界及分析产物；用户明确确认后才开始交付代码。

两处均支持输入 `y` / `确认` / `同意` 继续，输入修改意见重新整理，输入 `/pause` 暂停。空行忽略并继续等待，不会作为回答或暂停指令。终端输入关闭与非交互模式会明确记录暂停原因。修改测试方案时重新分析其对需求的影响；如果需求内容不变，已确认的需求不重复询问，修改后的方案仍需确认。修改已确认需求时不允许方案静默覆盖，必须重新确认需求。

确认记录保存在state.json、task.json和conversation.jsonl，含确认内容摘要及时间；当前测试方案单独维护为test_plan.md。`awaiting_confirmation`表示等待用户确认，非交互模式也会停在这里，不视为执行成功。

简单工程通常拆成核心、顶层、测试与说明等2至4项。复杂工程可以逐模块交付；关键性能含义不清楚时先提问，不应自行增加严格指标。

## 检查点与恢复

- `tasks.md`：清单、当前任务、交付和集成验证状态。
- `task.json`：任务状态和清单索引。
- `draft.json`：已交付文件的完整内容和交付记录，是恢复依据。
- `editing/*.json`、`working.md`：任务内暂存修改、累计摘要、下一步和读取窗口；最终交付前不进入draft。
- `events.jsonl`：任务选择、文件读取、交付和修复事件。
- `revisions/`、`runs/`：集成候选快照及真实工具执行证据。

失败或中断后，在需求不变的情况下执行：

```powershell
.\.venv\Scripts\python.exe main.py run --resume <任务编号> --continue --effort high
```

这会复用当前计划和检查点，跳过已交付文件，从未完成任务继续。集成失败后的恢复会使用最新修复草稿重新验证，当前初版仍会重跑集成仿真/构建，不按阶段缓存。已完成或等待现场验收的任务不会因该命令再次下载。

如果暂停在确认点，该命令会展示对应内容并等待确认，已确认内容不重新请求模型。旧任务没有确认记录时，首次继续需要确认现有需求和方案；已完成的任务不会被重新执行。

如果是补充回答或修改需求，使用：

```powershell
.\.venv\Scripts\python.exe main.py run --resume <任务编号> --request "修改后的需求或回答"
```

这会重新规划，旧草稿移入history，不复用旧的验证资格。旧版没有development_tasks的任务也用这个方式迁移，不能直接使用--continue。

开发小任务中的澄清请直接在提示处回答，或暂停后用 `run --resume <任务编号> --continue` 回答。回答会送回原编辑检查点，保留已暂存文件和确认过的需求/方案，不作为新的整体需求重新规划。`--request` 仍明确表示修改整体需求。

`full_task` 表示调度器当前分配的小任务，`task/next_step` 表示该任务内部的当前/下一步骤。文件满足当前小任务交付条件后，由模型返回 `deliver`；调度器再切换下一任务和可写范围。越界反馈包含当前任务、允许文件和已暂存文件，框架不会自动扩大权限或认定任务完成。

## 仿真前Python

系数生成分为两个任务：交付 `scripts/coefficients.py`，随后执行kind=python的任务，声明输入脚本及 `data/coefficients.hex` 等文本输出。脚本在新的隔离工作目录运行，不带参数；目录不是安全沙箱。只有本次执行成功且声明输出存在时才交付数据，旧输出不会被误用。失败会反馈真实日志，允许增量修复脚本。

数据导入草稿，最终进入project/data。XSIM运行前复制本次data，RTL使用 `data/文件名` 相对路径。数据也计入源码摘要，系数变更会使旧验证证据失效。

仿真后的自定义Python分析接口保持 `--input VCD --output 产物目录`。

## 修复和完成语义

集成失败后，模型读取错误相关文件，可有限轮次请求读取其他已交付文件，每轮修改最多3个文件。未修改文件和冻结规格保持不变，不要求重新输出整个工程。修改后重跑集成验证；存在预处理任务时重新生成数据。

集成修复阶段的 `available_tools` 提供 `execute` 时，模型可以先执行单个 Python 分析，再根据实际结果继续编辑或提交验证：

```json
{"action":"execute","script":"scripts/analyze_hw.py","input":"data/mock_vio.csv","outputs":["hardware_plot.png","hardware_report.md"]}
```

`script` 必须是当前工程已有的 `scripts/*.py`；修改先通过 `checkpoint` 暂存。`input` 可以是当前工程数据路径，也可以是本任务内已保存的 VCD/CSV 等文本数据路径。框架在新的运行目录复制当前源码与暂存内容，复用 Python 的 `--input/--output` 接口、超时、日志及产物保存能力，不覆盖正在使用的工程或比特流。此目录用于产物隔离，并不是操作系统安全沙箱。

执行结果立即返回当前模型会话并写入 `state.results` 和编辑检查点，包含真实命令、退出码、日志、输入来源、源码摘要及产物路径；失败日志和部分产物也保留。完整文本进入 `file_index`，暂停后可继续读取。退出码和声明产物检查只表示工具执行情况，功能结论仍由 DeepSeek 判断。

`verify` 交付当前修改并请求集成验证，`message` 中的命令文字不会被当作工具调用。仅补充执行证据而没有改变工程时，再审查复用已有成功仿真、分析和构建记录；任何工程修改仍重新集成验证。补充执行记录只对其对应的源码版本提供给审查，并改变审查检查点身份，避免复用补充证据之前的旧结论。模拟 CSV 的分析与真实 VIO 采样分别记录，前者不能替代下载或硬件验收。

## 范围与限制

每个计划最多24项，总文件最多32个。单轮最多3个交付文件，按需读取轮数和上下文大小有界。当前仍会向集成审查提供完整工程，任务拆分也不能保证模型在每一步都不耗尽思考预算；发生截断时不会应用残缺内容，已交付检查点仍可恢复。

框架始终保持用户指定的模型、思考强度和输出预算。客户端仍记录用量、实际请求参数、正文文件及耗时；JSON格式修复保留原有最多两次的机制，不负责把截断结果拼成完整JSON。

本地回归覆盖中断恢复、依赖错误、有限文件读取、增量修复保留未修改文件、Python真实执行和旧输出隔离。真实工具检查通过“脚本交付→生成系数→RTL和测试交付→XSIM读取系数→Python绘图”，记录位于 `.validation/incremental-*/verification.json`。该检查使用固定模型响应，不代表真实DeepSeek复杂信道化项目已验证成功；本次未上板。
